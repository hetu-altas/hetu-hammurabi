## 一、任务要求

### 需求背景

现有 hetu-hammurabi 宪章体系基于 opencode 的 Commands / Agents / Skills / Plugins 实现，理念与分层设计（软约束宪章 + 硬门禁插件 + 状态固化 + 资产沉淀）已被验证有效，但存在以下**机制级缺陷**（本次重构必须全部修复）：

| 编号 | 缺陷 | 证据 / 位置 |
|------|------|------------|
| D1 | **门禁跨任务串门**：`.gate.json` 由 `findAllGateFiles` 递归扫描整个 `opencode_schedule/` 并排序取最新，不限定当前任务。任何历史/并行任务的 `test_passed=true` 都会误开当前任务门禁 | `.opencode/plugin/charter-gate.ts` L19-48；佐证：20260809 任务1 状态文件在测试节点前已写入节点 -1/0/1/2 记录 |
| D2 | **门禁自写自验**：`.gate.json` 由被约束对象 charter-tester 自行写入，`write` 工具不受任何拦截，任何代理可手写 `{"test_passed": true}` 伪造开闸 | `charter-tester.md` + `charter-gate.ts`（无写入方校验） |
| D3 | **编排指令与门禁冲突**：编排器要求每完成一个节点就写 `研发流程状态.md`，门禁却在开闸前拦截该文件写入——两规则在节点 1/2 直接矛盾，当前靠 D1 串门歪打正着 | `charter-orchestrator.md` 状态跟踪节 vs `charter-gate.ts` L113-123 |
| D4 | **硬拦截覆盖面窄可绕过**：① 通知仅匹配 bash 命令中的 `util_dingtalk|send_markdown|send_text`，`curl`/`requests` 直发 webhook 即绕过；② 危险命令仅匹配**行首** `rm -rf`（`echo x && rm -rf` 绕过）、仅查 "backup/备份" 字样；③ 日志文件名硬编码中文 | `charter-gate.ts` L113-129 |
| D5 | **流程定义硬编码**：节点顺序、回退轮次（3/2）、门禁挂载点全部写在系统提示词里，不可版本化、不可扩展、依赖模型数数 | `charter-orchestrator.md` 流程节点节 |
| D6 | **无运行度量**：节点运行次数/成功率/门禁拦截率/失败原因无采集，无法反哺宪章修订 | `docs/harness/extend.md` 已知限制表 |

**用户新增需求**：基于 **DSH（DeepSeek Harness，`@deepseek-ai/dsh`，cordis 插件化 profile 体系，含 web GUI / headless / client-plugin 扩展点）** 重构整套体系，并新增**可视化数据看板**：展示各节点运行次数、成功率、门禁拦截率、每个任务的运行情况（节点时间线、事件明细）。

### 目标

1. **宪章不变**：`constitution/` 单一权威零改动（或仅登记性改动），宪章思想（人是立法者、宪法高于对话、软硬分层）完整保留，仅重构执行载体与机制层
2. **载体迁移**：将 opencode 的 Commands / Agents / Skills / Plugins 映射到 DSH 的 profile / 插件 / agent / skill / client-plugin 机制，建成 `harness/` 新目录；保留 `.harness-env` 拓扑契约与 `opencode_schedule/` 目录契约（历史任务数据兼容）
3. **缺陷全修复**：D1-D5 全部关闭，并有回归测试固化
4. **数据看板**：DSH web GUI 内新增看板面板（或独立路由），实时/准实时展示运行统计与任务详情，数据来自真实运行事件
5. **自举验收**：新体系自身跑通一个验收小任务（单工具方法级），全节点 -1~7 通过

### 验收标准（可逐条验证）

1. **串门回归**：构造 2 个任务目录并存（A 已开闸、B 未测试）的场景，B 在测试前写日志/发通知一律被拦；A 的闸不影响 B（单测 + 集成场景双重验证）
2. **伪造拦截**：任何代理直接 `write` 伪造 `.gate.json`（含正确的 `test_passed: true` 但无有效 token / run_id 不匹配）不生效，门禁保持关闭
3. **绕过面回归**：`curl`/`requests` 外呼钉钉、`echo x && rm -rf`、重命名后的日志文件写入、非行首危险命令，全部被拦
4. **看板可用**：DSH web 打开看板，可见：总览（任务数/节点运行次数/成功率/门禁拦截率）、按节点统计、按任务列表与详情（节点时间线 + 事件流），且能统计 20260804/20260809 历史任务
5. **自举**：新体系执行验收小任务，产出任务书/实施计划/代码/测试/`.gate.json` v2/日志/资产登记全链路产物，状态文件逐节点固化
6. **兼容**：hetu-mercury / hetu-thoth / hetu-sybil 无需改业务代码，仅重跑安装脚本即接入新体系；`constitution/` 零改动

## 四、接口 / 数据格式定义

### 4.1 运行事件流（run_event，JSONL，一行一事件）

- 落盘：`runlog/events/YYYYMMDD/<run_id>.jsonl`（追加写，不覆盖）
- **run_id 契约**：`run_id` = 任务目录名（`opencode_schedule/<YYYYMMDD>/<任务目录>/` 的目录名）。门禁判定、事件采集、看板聚合**全部以 run_id 为键**——这是修复 D1 的根本手段

```json
{
  "event_id": "uuid",
  "ts": "2026-08-14T10:00:00+08:00",
  "run_id": "20260814任务1xxx",
  "project": "hetu-thoth",
  "node": "3",
  "node_name": "单元测试",
  "event_type": "node_start | node_end | gate_block | gate_pass | retry | notify | error",
  "status": "running | pass | fail | blocked",
  "round": 1,
  "detail": {"msg": "…", "tool": "bash", "file": "…"},
  "extra": {}
}
```

### 4.2 `.gate.json` v2（信任模型重构，修复 D1/D2）

```json
{
  "schema_version": 2,
  "run_id": "20260814任务1xxx",
  "task_dir": "opencode_schedule/20260814/20260814任务1xxx/",
  "test_passed": true,
  "total": 20, "passed": 20, "coverage": 0.87,
  "written_by": "charter-orchestrator",
  "result_files": ["unit_test/test/test_xxx_result.txt"],
  "gate_token": "<HMAC-SHA256(run_id + 结果摘要, 宿主密钥)>",
  "updated_at": "2026-08-14T10:00:00+08:00"
}
```

**写/验分离**：charter-tester 只负责运行测试并写 result 文件；**落闸权上收**——charter-orchestrator 核对全部 result 文件 PASS 后写 `.gate.json` v2 并计算 `gate_token`；gate 插件开闸条件 = ① `run_id` 等于当前会话任务目录名 + ② token 校验通过 + ③ 时间戳新鲜（≤ 10 分钟）。三者缺一即 fail-closed。

### 4.3 `workflow.yaml`（流程定义外置，修复 D5）

```yaml
schema_version: 1
nodes:
  - id: -1
    agent: charter-taskwriter
    when: input_is_requirement      # 仅一句话需求输入时执行
  - id: 0
    agent: builtin_validate         # 内建：任务书/宪章/输出目录校验
  - id: 1
    agent: charter-analyst
    outputs: ["实施计划.md"]
  - id: 2
    agent: charter-coder
  - id: 3
    agent: charter-tester
    gate: unit_test                 # 硬门禁：.gate.json v2 校验
    retry: {to: 2, max_rounds: 3}   # 失败回编码，最多 3 轮
  - id: 4
    agent: charter-reviewer
    gate: review                    # 评审结论 APPROVE 才放行
    retry: {to: 2, max_rounds: 2}
  - id: 5
    agent: charter-logger
    requires: [3, 4]
  - id: 6
    agent: charter-assetter
    requires: [3, 4]
  - id: 7
    agent: charter-notifier
    requires: [3, 4]
```

编排插件解析并执行本文件；新增/调整节点只改 yaml，不碰插件代码。

### 4.4 看板查询 API（本地 HTTP 服务，由采集插件提供）

| 接口 | 返回 |
|------|------|
| `GET /api/stats/overview` | 任务总数、节点运行总次数、总体成功率、门禁拦截率、周期（按日/周/月） |
| `GET /api/stats/nodes` | 每节点：运行次数、成功/失败数、成功率、平均轮次、最近 10 次趋势 |
| `GET /api/stats/gates` | 门禁拦截事件列表（时间/任务/节点/原因）+ 拦截率 |
| `GET /api/tasks` | 任务列表（run_id/项目/日期/最终状态，支持过滤） |
| `GET /api/tasks/<run_id>` | 任务详情：节点时间线、事件流、产物文件清单、门禁记录 |

**口径约定**：成功率 = 节点成功次数 / 节点运行次数（含重试轮次）；门禁拦截率 = 门禁拦截次数 / 门禁检查次数；历史任务（无事件库时期）按 `opencode_schedule/` 存量文件（状态文件 + `.gate.json` v1）静态解析一次并入统计，并在看板标注"历史数据（解析）"来源。
