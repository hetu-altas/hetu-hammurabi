## 第 1 章 项目定位与职责边界

### 1.1 hetu 项目体系全景

hetu 体系共五个项目，部署于同一父目录 `/mnt/d/workspace/hetu-altas/`，共享 `venv-hetu` 虚拟环境（宪章第二条、第三条）：

| 项目 | 定位 | 职责 | 关键资产 |
|------|------|------|---------|
| **hetu-hammurabi** | harness 宿主（宪章编程） | 宪章规范、流程编排（charter-orchestrator + 节点子代理）、硬约束插件（charter-gate）、资产登记（资源地图）、任务模板 | `constitution/`、`.opencode/`、`docs/harness/`、`templates/task_book.md` |
| **hetu-aether** | 公共工具（代码资产） | 配置管理、数据库连接池、日志、钉钉、Milvus 检索、交易日历等通用能力 | `utils/util_*.py`、`conf/*.json` |
| **hetu-mercury** | 数据同步引擎 | Tushare 采集/同步，GreatSQL（关系）+ TDengine（时序）双库落库 | `src/batch/sql/`（DDL）、`src/fetch_tushare_data/`（采集）、`interface/`（接口清单） |
| **hetu-thoth** | 文档/知识处理 | 8 类非结构化数据源 → 下载 → 转 MD → JSONL → Batch Embedding → Milvus `thoth_knowledge` | `src/download_files/`、`src/convert2md/`、`src/text2jsonl/`、`src/indexing/`、`scripts/weekly_pipeline.sh` |
| **hetu-sybil** | **量化投研分析模块（本项目）** | 基于 harness 能力执行投资分析动作与投资决策：基本面/宏观/研报/新闻/个股/评级六大分析 → AI 决策研判 → 决策产出 | `docs/架构与模块设计.md`（本文件，首个资产） |

### 1.2 hetu-sybil 定位

hetu-sybil 是 hetu 体系的**分析层与决策层**：所有分析动作基于 opencode harness 能力（子代理 / 技能 / MCP / 插件 / 门禁）执行，以 AI 代理为核心进行投资决策。Sybil（西比尔）寓意"预言者"——从多源数据中洞察并输出投资判断。

**投资约束（已确认）**：中低频投资——日频信号、周频决策，持有周期周~季度；仅使用**自有资金**，**不加杠杆**；决策层产出决策建议（决策摘要 JSON + 决策报告 + 仓位建议，综合评分由 AI 给出），**不含交易执行链路**（不连接券商/下单）。因此本设计聚焦"分析→决策建议→复盘反馈"闭环，无交易域组件。**验证范式（2026-08-13 用户确认）**：本体系验证范式 = **前向验证 + 复盘归因（非回测）**——AI 研判决策不可重放（无固定策略可测）、中低频判断依赖当下、人做最终决策，回测的平稳性/可重放/参数优化三前提在 AI 研判体系不成立；验证路径 = 信号与决策记录（signal_log，任务 2 接口 / 任务 9 决策摘要 JSON 存档）→ 后续实际行情对照 → 复盘模块（3.7 节）命中率统计/决策归因/模块有效性 → 研判口径与关注池迭代；代码级候选预筛参数仅做**数据核对**（轻量统计，非策略回测）。

依赖关系（自下而上）：

```
hetu-mercury（数据供给：GreatSQL/TDengine）
        ↓
hetu-thoth（知识供给：Milvus thoth_knowledge 向量检索）
        ↓
hetu-aether（工具供给：DB 连接池 / 日志 / 钉钉 / Milvus 检索 / 日历）
        ↓
hetu-hammurabi（流程供给：harness 编排 / 门禁 / 资产登记 / 宪章约束）
        ↓
hetu-sybil（分析 + 决策）
```

### 1.3 职责边界（"四不重复"原则）

| 边界 | 说明 |
|------|------|
| **不重复采集** | 数据获取全部复用 hetu-mercury 已同步落库的关系表/超级表；sybil 不写采集代码 |
| **不重复向量化** | 非结构化数据（研报/新闻/公告等）复用 hetu-thoth 的下载→转 MD→JSONL→Embedding→Milvus 链路；sybil 不重复建库建 collection |
| **不重复工具实现** | DB 连接、日志、钉钉、Milvus 检索、交易日历一律复用 hetu-aether `utils/`，禁止在 sybil 内重复实现（宪章第八条） |
| **不重复流程** | 研发流程（任务书→分析→编码→单测→评审→日志→沉淀→通知）复用 hammurabi harness 工作流，通过 `/cc <任务书路径>` 触发（`hetu-hammurabi/.opencode/commands/cc.md`） |

**hetu-sybil 新增的资产**：分析/决策域——七大模块的分析逻辑、信号定义、聚合决策、复盘反馈、投研专属代理/技能/命令/插件/门禁及私有配置（五类专属能力口径见 5.6 节），以及本类设计文档。

### 1.4 对上游项目的约束（设计前提）

1. 数据可用性依赖 mercury 的**同步状态**（DDL 存在 ≠ 数据已落库），因此分析层必须内置"数据完整性/新鲜度校验"门禁（见 5.5 节）。
2. 知识可用性依赖 thoth 周度流水线的**运行结果**（`weekly_pipeline.sh` 四阶段），检索前须确认 Collection 存在与数据新鲜度。
3. 所有连接配置从 `<AETHER_DIR>/conf/*.json` 读取，禁止硬编码（宪章安全底线第 4 条）。

### 2.3 知识层（Knowledge Layer）

**职责**：将非结构化数据转化为可检索知识，向分析层提供语义检索能力（研报观点、新闻舆情、公告、政策等）。

| 组件 | 说明 | 依赖资源 |
|------|------|---------|
| 知识生产链路（thoth 侧，sybil 只消费） | 8 类数据源：个股研报、行业研报、新闻、重大新闻、CCTV 新闻、国家政策(npr)、互动易(irm_qa_sh/sz)、公告(anns_d)；链路 下载→转MD→JSONL→Batch Embedding→入库 | 下载 `hetu-thoth/src/download_files/`（download_research_report.py、download_anns_d_pdf.py、convert_npr_to_markdown.py）；转MD `hetu-thoth/src/convert2md/`（convert_stock_report_to_md.py、convert_industry_report_to_md.py、convert_anns_d_to_md.py 及 _gpu 版）；JSONL `hetu-thoth/src/text2jsonl/`（build_stock_report_jsonl.py、build_industry_report_jsonl.py、build_news_jsonl.py、build_major_news_jsonl.py、build_cctv_news_jsonl.py、build_npr_jsonl.py、build_irm_qa_sh/sz_jsonl.py、build_anns_d_jsonl.py、submit_batch_embedding.py）；入库 `hetu-thoth/src/indexing/`（create_collection.py、insert_vectors.py） |
| 周度流水线 | npr/stock_report/industry_report 三源"拉取→转MD→向量化入库"（四阶段 download/convert/vectorize/poll-only） | `hetu-thoth/scripts/weekly_pipeline.sh`；沉淀指南 `hetu-hammurabi/docs/hetu-thoth/cron/weekly_pipeline_guide.md`（注意：该指南仅存于 harness 宿主资产区，thoth 项目内无 docs/cron 目录） |
| 向量检索 | 两级召回：先元数据过滤缩小候选集、再向量检索 | `hetu-aether/utils/util_milvus.py` `recall`（L510，签名见 4.2.1 节） |
| 分块策略 | H2 标题分段→section 字段、短章节合并、递归切分、短 chunk 合并、表格保护/截断 | `hetu-thoth/docs/text2jsonl/stock_report_jsonl_guide.md` 第四章 |

**向量库 Schema 要点**（`hetu-thoth/docs/indexing/indexing_guide.md` 第九章，21 字段，引用时以该文档为准）：
`id`（VARCHAR(256)，格式 `{source}_{source_id}`）、`source`（VARCHAR(32) 数据源标识）、`source_id`、`title`、`publish_date`、`content`（VARCHAR(65535) 向量化原文）、`vector`（FLOAT_VECTOR(1024)，text-embedding-v4）、`chunk_index`/`chunk_count`、`section`、`stock_code`、`stock_name`、`institution`、`industry`、`report_type`、`ann_type`、`publisher`、`doc_id`、`category`、`channel`、`src`；索引：vector HNSW(M=16, efConstruction=200, metric=IP) + `publish_date`/`source`/`stock_code` INVERTED。

> 8 类数据源的 `source` 取值由各 build 脚本写入，检索过滤即以此为一级筛选维度（见 4.2.1 节示例）。

**职责**：六大分析模块各自完成"取数 → AI 分析研判 → 出信号"，输出标准化信号 JSON（格式见 4.2.3 节，**AI 输出契约**：schema 已由任务 2 冻结，AI 输出侧遵守）。模块详见第 3 章。

| 组件 | 数据来源 | 输出 |
|------|---------|------|
| 基本面分析模块 | GreatSQL 财务表（income/cashflow/fina_indicator/fina_audit/fina_mainbz/forecast/express/dividend） + **Milvus 文本**（anns_d 公告/stock_report 研报/irm_qa 互动易，文本为主） | 基本面信号 |
| 宏观数据模块 | TDengine 宏观经济 18 超级表 | 宏观环境信号 |
| 研报模块 | Milvus `thoth_knowledge`（source=stock_report/industry_report，核心） | 研报信号 |
| 新闻模块 | Milvus `thoth_knowledge`（source=news/major_news/cctv_news/irm_qa_sh/irm_qa_sz/anns_d/npr） | 舆情信号 |
| 个股数据分析模块 | TDengine 行情/资金超级表 + GreatSQL 股东表 | 技术/资金信号 |
| 研报机构评级模块 | GreatSQL `report_rc`/`broker_recommend`（**待确认**：同步状态）+ Milvus 交叉验证 | 评级信号 |

### 2.5 决策层（Decision Layer）

**职责**：投研决策代理（sybil-decision）读取各模块信号 JSON + 证据链，**AI 综合研判**（依据证据强度动态权衡，**无固定权重表**）→ 输出决策摘要 JSON（综合评分/方向/仓位建议，score 由 AI 给出）→ 生成投资决策报告文本与仓位建议（推荐形态：**决策摘要 JSON + 决策报告文本 + 仓位建议**，备选：仅信号；**待确认**，见 7.3 节待确认2；投资约束见 1.2 节）。

| 组件 | 说明 |
|------|------|
| AI 决策研判（投研决策代理） | 按 ts_code/日期对齐多模块信号，读取各模块信号 JSON 与证据链，**由 AI 综合研判**（依据证据强度动态权衡，**无固定权重表**、无规则打分公式） |
| 决策摘要 JSON 输出 | 输出决策摘要 JSON（AI 输出契约，由 decision-report 提示词模板承载）：综合评分（0~100，score 由 AI 给出）、方向（bull/bear/neutral）、仓位建议、证据链引用；经校验门禁后供记录/复盘/统计引用 |
| 决策报告生成 | 由投研决策代理基于决策摘要 JSON 产出研究报告文本（含证据链引用与风险提示） |

### 2.6 交互/通知层（Interaction/Notification Layer）

**职责**：对外输出决策结果、研发通知与告警。

| 组件 | 说明 | 依赖资源 |
|------|------|---------|
| 钉钉通知 | 决策结果推送、流水线失败告警 | `hetu-aether/utils/util_dingtalk.py`（send_markdown / send_text） |
| 日志 | 统一日志（含项目名/文件名/方法名/时间戳/操作名/状态/耗时） | `hetu-aether/utils/util_log.py`（get_logger/log_operation）；输出目录 `../logs/hetu-altas/hetu-sybil/`（宪章第七条） |
| 交互入口 | 研发期经 harness `/cc` 命令触发开发流程；运行期经 sybil 私有命令（`/analyze`，任务11 落地）触发分析任务 | `hetu-hammurabi/.opencode/commands/cc.md`（研发入口）、`hetu-sybil/.opencode/commands/analyze.md`（私有入口，任务11 落地） |

### 2.7 横切关注：harness 能力注入点

- **分析动作**由**投研专属子代理**驱动（5.1 节），通过**专属技能**固定分析流程（5.2 节）；

### 3.1 基本面分析模块

#### 4.2.1 知识检索接口（`util_milvus.recall`，既有）

签名（`hetu-aether/utils/util_milvus.py` L510，已核实）：

```python
def recall(self, vectors: list, top_k: int = 10,
           metadata_filter: Optional[str] = None,
           output_fields: Optional[List[str]] = None,
           pk_field: str = "id", metadata_limit: int = 1000,
           name: Optional[str] = None) -> dict
```

- 两级召回：一级 `metadata_filter` 非空时标量 query 取候选主键（上限 `metadata_limit`）→ 二级在候选内向量检索；无过滤退化为纯向量检索；
- 返回：`{"candidates": 候选集大小(None=未过滤), "results": 检索结果列表}`；
- 过滤表达式为 Milvus filter 语法，例：`source == "stock_report" and stock_code == "000001.SZ" and publish_date >= "2026-07-01"`；
- 约定：检索前先 `get_milvus(project_name="hetu-sybil")` 取单例（`util_milvus.py` L712），用完释放；Collection 名默认取 `conf/milvus_conf.json` 的 `collection_name`（thoth_knowledge），也可经 `name` 显式指定。

**研报/新闻模块调用示例（契约）**：

| 用途 | vectors | top_k | metadata_filter | output_fields |
|------|---------|-------|-----------------|---------------|
| 个股研报检索 | 问题文本 embedding（经 thoth util_text_embedding 或 model_conf 配置的模型） | 20 | `source == "stock_report" and stock_code == "000001.SZ"` | `title, publish_date, content, section, institution, report_type` |
| 舆情检索 | 同上 | 30 | `source in ["news","major_news","cctv_news"] and category == "..."` | `title, publish_date, content, category, channel, src` |

### 4.3 决策产出流程

1. **触发**：研发期经 `/cc <任务书>` 触发开发流程；运行期经 sybil 私有命令（`/analyze`，任务11 落地）或定时任务唤起投研决策代理；
2. **取数与分析**：各模块子代理按第 3 章动作执行，产出各模块信号 JSON（含基本面文本/Milvus 检索）；
3. **门禁检查**：数据完整性（新鲜度/覆盖率，见 5.5）→ 不合格则该模块信号标记降级或弃用；
4. **聚合（AI 决策研判）**：决策层按 ts_code+日期对齐信号，投研决策代理读取全部模块信号 JSON 与证据链，**AI 综合研判**（依据证据强度动态权衡，**无固定加权规则**）；
5. **决策生成**：投研决策代理基于 AI 综合研判结论输出决策摘要 JSON + 生成决策报告文本与**仓位建议**（投资约束见 1.2 节：自有资金、不加杠杆、无交易执行链路）；**决策摘要 JSON 与信号记录（signal_log）构成前向验证数据基础**（验证范式非回测，2026-08-13 用户确认），供任务 10 复盘归因与命中率统计；
6. **合规校验**（插件扩展，见 5.4）：决策输出合规校验（免责声明、敏感词）；
7. **输出与通知**：报告落盘 + `util_dingtalk.send_markdown` 推送摘要；
8. **信号与决策持久化**：本次各模块信号 JSON 与决策产出写入信号/决策记录（存储形态**待确认**，见 7.3 待确认5；任务 2 定义接口、任务 10 落地），供复盘模块（3.7）引用。

### 4.5 分析流水线（重构：模板 + 实例化）

> **架构理念（2026-08-12 用户确认）**：1 条流水线 = 1 次分析任务（标的 1~N 只 + 模块 + AI 研判档位），与 `/cc` 同构；批量 ≠ 多次实例化；内部批量处理、深度研判仅聚焦子集；不设巨型流水线；**分析由 AI 主导（代理+技能），代码仅取数**（analyze_stocks 取数与视图组织、无信号，为筛选工具 + 流水线内批量取数与视图组织工具，见 4.5.4）。

#### 4.5.1 设计原则

1. **一任务一流水线**：1 条流水线 = 1 次分析任务（标的 1~N 只 + 模块 + AI 研判档位），内部批量处理（取数 query_batch/数据视图按 N 只批量，AI 研判按档位覆盖）；批量 ≠ 多次实例化；不设"全量大流水线"。
2. **模块代码为流水线内步骤工具**：data_access（含 `query_batch`）、数据视图组织、信号校验/记录等为步骤工具，不构成流水线；代码只取数与视图组织，分析判断由 AI 代理完成。
3. **sybil-decision 为编排者**：调度步骤、控制 AI 研判档位与聚焦子集范围。

#### 4.5.2 分析流水线模板（统一，步骤可配置裁剪）

| 步骤 | 内容 | 裁剪性 |
|------|------|--------|
| ① 数据就绪校验 | 新鲜度/覆盖率批量校验（4.4/5.5），代码执行，结论供 AI 引用 | 必选 |
| ② 批量取数 | query_batch 一次 N 只；组织 AI 可读数据视图（行情+基础统计/资金/股东，任务 3） | 必选 |
| ③ AI 分析步骤 | sybil-research-analyst 读数据视图 → **加载对应提示词模板（analysis-flow 技能提供，随提示词模板体系按模块/层级匹配，见 5.2）** → 按 analysis-flow 技能研判 → 信号 JSON（evidence 引用视图） | 必选（按目标裁剪） |
| ④ 知识增强 | recall 研报/新闻 + AI 解读，仅聚焦子集（候选 top K/事件/指定） | 可选（深度档必含） |
| ⑤ 批量校验+记录 | signal-validator 校验 + signal_record 写入（JSONL，任务 10），按标的批量 | 必选 |
| ⑥ 报告/通知 | decision-flow AI 决策研判 + 决策/复盘报告 + 钉钉推送 | 可选 |

**AI 研判档位**（实例化配置；聚焦子集与标的总数解耦）：

> 轻量研判 = N 只全量 AI 短输出；标准分析 = 全量研判 + 聚焦子集详细分析；深度分析 = 聚焦子集全链（视图 + recall 研报/新闻 + 完整研判）。（原三档「代码级/摘要级/深度级」废弃，统一为 AI 档位，见修订记录）

| 档位 | 步骤范围 | 说明 |
|------|---------|------|
| 轻量研判 | ①~③+⑤~⑥（全部标的） | N 只全量 AI 短输出；默认 S1 日频例行 |
| 标准分析 | ①~③（全部）+④（聚焦）+⑤~⑥ | 全量研判 + 聚焦子集知识增强；默认 S4 月度宏观 |

#### 4.5.3 触发场景（调度入口，非流水线本体）

> 场景 = 调度入口（cron/事件检测/手动），发起分析任务（实例化流水线模板）；场景本身不是"一条大流水线"；多条流水线可并行。

#### 4.5.4 代码级预筛（筛选工具，非流水线本体）

- 全市场/关注池**代码级候选生成**（`analyze_stocks`，任务 3）：批量取数 + 数据视图组织，基于基础统计特征（涨跌幅/成交额/资金净额等数据加工字段）产出候选清单——**不含任何规则信号**，**不称为"流水线"**；同时是流水线内步骤②批量取数与视图组织的直接工具（无需重复实例化）。

### 5.5 门禁（Gates）

**决策流程质量门禁（设计）**：

| 门禁 | 触发时机 | 规则 | 失败处理 |
|------|---------|------|---------|
| 数据完整性校验 | 各模块取数后 | 新鲜度（meta.data_freshness 距当前 ≤ 配置阈值）、覆盖率（关键表有数据、行数 > 阈值） | 校验结论写入数据视图 `meta.data_freshness`/`evidence` 供 AI 引用；降级/弃用由 AI 研判执行（代码不预设信号降级规则） |
| 检索结果校验 | recall 返回后 | 命中数 ≥ 阈值（如 3 条）、top 相似度 ≥ 阈值（metric=IP） | 证据权重由 AI 依据检索质量动态权衡；0 命中由 AI 处置（置 neutral 或弃用并说明） |
| 决策合规审查 | 决策报告生成后 | 5.1 风险审查代理软审查 + 5.4 插件硬校验 | REJECT → 回退投研决策代理修改（最多 2 轮） |
| 研发门禁（既有） | 研发流程节点 2→3 | `.gate.json` 测试门禁（charter-gate 硬阻断） | 测试未通过禁止进入日志/通知节点 |

**与 `.gate.json` 机制的关系**：`.gate.json`（`charter-gate.ts` 读取的事实来源，字段含 test_passed）是**研发流程**的硬门禁事实文件，由 charter-tester 写入任务目录；本文设计的"数据完整性/检索结果/合规审查"门禁属于**投研决策运行期**的质量控制，**不写入 `.gate.json`**，而是作为分析/决策流程内的校验步骤（可复用 charter-gate 的 throw 拦截模式做决策链路硬校验）。二者层次不同：前者约束"研发流程能否推进"，后者约束"投研决策能否产出"。
